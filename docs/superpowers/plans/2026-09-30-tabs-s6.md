**Goal:** drag a tab along the bar to move it. It lands at the index of the
tab it is dropped on. The active tab, the MRU, every tab's place and history
and the closed stack stay as they were. The target shows where the tab will
land while the button is held.

**Spec:** `docs/superpowers/specs/2026-09-29-tabs-design.md`: decision 6, A1
invariant 3 ("A reorder changes neither the MRU nor the active id"), A5 (the
bar), As built S1 (`keep_active_tab_visible`, T4). Rules: `CLAUDE.md`,
`.claude/rules/{shell,app-tests,gpui}.md`.

## Decisions settled from the code

1. **The gesture is gpui's drag and drop, as Zed's tab bar.** Each tab gets
   `on_drag`, `drag_over` and `on_drop` (`vendor/zed-reference/crates/workspace/src/pane.rs:2953-2995`,
   `P` below). In gpui (`vendor/zed-reference/crates/gpui/src/elements/div.rs`, `D`):
   - A left press records a pending mouse-down (`D:2947-2961`). A move more
     than `DRAG_THRESHOLD` = 2 px away (`D:52`) with the press pending builds
     the preview from `on_drag`'s constructor, sets `cx.active_drag`, and
     **takes the pending mouse-down** (`D:2966-3007`). So a drag fires no
     click: dragging an inactive tab does not activate it.
   - At mouse-up, a drop listener runs in the bubble phase when its hitbox is
     hovered and the drag's type matches (`D:2897-2926`). Anything else
     cancels the drag: the window clears `active_drag` after a mouse-up
     (`gpui/src/window.rs:5791-5800`).
   - `drag_over::<T>` refines the style while a `T` is dragged over the
     element (`D:1185-1201`, applied `D:3473-3500`).
   - The preview is drawn at the window root, at the pointer less the press
     offset (`window.rs:3554-3571`). It inherits no style from the bar.
2. **The drag value, after Zed's `DraggedTab`** (`P:523-530`, render
   `P:5055-5080`), in `shell/tab_bar.rs`:

   ```rust
   /// The tab under the pointer; also its preview. `index` is where it stood when the drag began.
   #[derive(Clone)]
   pub(super) struct DraggedTab { id: TabId, index: usize, title: SharedString, active: bool }
   impl Render for DraggedTab { /* one tab's look: px_2, UI size and line height, its colours */ }
   ```

   The drop reads `id`, stable across a reorder or a close; `index` only
   picks the indicator's side. The preview is a plain `div` with no id and no
   listener, so it inserts no hitbox and cannot occlude the target's hit test
   (`window.rs:1106-1123`, cited in `shell/modal.rs:119`).
3. **The model: `Tabs::move_tab`, Zed's index rule.** Zed's drop removes the
   item and inserts it at the target's index, clamped after the removal
   (`add_item_inner`, `P:1266-1275`, `P:1297-1318`). Dropping tab 0 on tab 2
   gives `[1, 2, 0]`; tab 2 on tab 0 gives `[2, 0, 1]`.

   ```rust
   impl<P> Tabs<P> {
       /// Moves tab `id` to `to`, clamped to the bar; the MRU and the active id stay (invariant 3).
       /// Nothing for an id that is no tab: it closed during the drag.
       pub fn move_tab(&mut self, id: TabId, to: usize);
   }
   ```

   In `impl<P> Tabs<P>` (`crates/tabs/src/lib.rs:119-184`): it needs no
   `Place`. It takes no `leaving`, since no tab is left. It returns nothing;
   the app notifies either way.
4. **Deviations from Zed**, each recorded in As built:
   - **A drop does not activate the tab.** Zed's `move_item` activates and
     focuses it (`workspace.rs:12154-12195`, `activate = true`; `P:1321`).
     Invariant 3 keeps the active id, and the drag already suppressed the
     click.
   - **No drop target after the last tab.** Zed adds one to the bar
     (`render_tab_bar_drop_target`, `P:3697-3742`) because a drop may come
     from another pane. Here, a drop on the last tab puts the tab last. The
     bar's children stay the tabs only, so `scroll_to_item` still indexes
     tabs (`shell/tab_bar.rs:32`).
   - **No split zones, no cross-pane move, no ⌥-drag clone, no path or
     selection drops** (`handle_tab_drop`, `P:3861-3960`): one pane, one bar.
   - **The indicator is Zed's** (`P:2963-2976`): the target's background,
     and a 2 px border on the side the tab will land, left when the target
     stands before the dragged tab, right when after. Its colours and width
     come from `theme.rs`, never a literal.
5. **The app handler is a reorder, nothing more.** In `shell/tabs.rs`:

   ```rust
   /// A drop in the bar: nothing is left, captured or parked, so a pending open still lands (T4).
   pub(super) fn move_tab(&mut self, id: TabId, to: usize, cx: &mut Context<Self>) {
       self.tabs.move_tab(id, to);
       self.keep_active_tab_visible();
       cx.notify();
   }
   ```

   - **No `dismiss_modal`.** A picker's backdrop occludes the bar and a left
     press on it dismisses the picker (`shell/modal.rs:119-129`). A drag
     therefore cannot start under a picker.
   - **T4's fifth no-op case.** The active tab and its note stay, so
     `activation` stays: an `open_note` commits into the same `TabId`
     (`activation.rs:20-38`), and an `open_in_new_tab` landing inserts at the
     active tab's new `active_index() + 1` (`shell/tabs.rs:93-98`).
   - **`keep_active_tab_visible` stays** (As built S1: every change to the
     tab set ends with it). A drop can push the active tab past an edge: with
     the tab right of it dropped on a tab left of it, it shifts right by that
     tab's width. After the user scrolled the bar off the active tab, a drop
     scrolls back to it, as a close does (Risks).
6. **Tests drag through real mouse events.** `VisualTestContext` has
   `simulate_mouse_down`, `simulate_mouse_move(position, button, modifiers)`
   and `simulate_mouse_up` (`gpui/src/app/test_context.rs:889-932`). A test
   window draws after each event's effects (`gpui/src/app.rs:1817-1831`), and
   hit tests run on every mouse event (`window.rs:5752-5756`). One helper:

   ```rust
   /// Presses on `from`, moves past gpui's 2 px threshold (div.rs:52), onto `to`, and releases there.
   fn drag(cx: &mut VisualTestContext, from: &'static str, to: &'static str)
   ```

   Zed's own tests call `handle_tab_drop` directly (`P:5986-6100`). Real
   events are chosen because the threshold, the suppressed click and the
   hover test are the behaviour under test. The first app test is red on
   today's code, which proves the helper: no `on_drag`, no drop, no move.
7. **The shot needs tab positions.** The shot `Stage` reads no
   `debug_bounds` (it is `VisualTestContext`-only, `test_context.rs:982`).
   `AppShell::tab_center(ix)` under `#[cfg(feature = "shot")]` reads
   `tab_scroll.bounds_for_item(ix)` (`D:4311-4313`); `Stage` gains
   `drag_holding(window, from, to)`: press, two moves, no release, settle.
8. **Theme.** `theme.rs` gains, after `TAB_MAX_WIDTH` (`:127`):
   `tab_drop_background()`, `tab_drop_border()`, and
   `TAB_DROP_EDGE: Pixels = px(2.)`. Proposed values: `rgba(0x4ea1ff26)`
   and `rgb(0x4ea1ff)`, the caret's blue (`theme.rs:73-75`), judged on the
   shot. `border_l(width)` and `border_r(width)` exist on a
   `StyleRefinement` (`gpui_macros/src/styles.rs:335-348`, custom setters),
   as `border_b(theme::RULE_WIDTH)` already shows (`tab_bar.rs:92`).

## Invariants

- **R1 (3):** `move_tab` changes neither the MRU nor the active id, nor any
  tab's place or stacks, nor the closed stack.
- **R2:** after `move_tab(id, to)`, `id` stands at `min(to, count - 1)`;
  the other tabs keep their relative order.
- **R3:** `move_tab` of an id that is no tab changes nothing.
- **R4 (app):** a drag calls no closure: nothing is captured, parked or
  unparked (I1, I2 hold), no undo group is sealed, focus stays, and a
  pending open still lands (T4).
- **R5 (app):** a drag fires no click: the dragged tab is not activated.
- **R6 (app):** after a drop, the active tab is inside the bar.
- **R7 (app):** a drop anywhere but a tab moves nothing, and no drag
  remains afterwards.

A tab in `render_tab_bar` (`tab_bar.rs:40-80`), after `on_aux_click`:

```rust
.on_drag(DraggedTab { id, index: ix, title: title.clone(), active: is_active }, |tab, _, _, cx| {
    cx.new(|_| tab.clone())
})
.drag_over::<DraggedTab>(move |style, dragged, _, _| {
    let style = style.bg(theme::tab_drop_background()).border_color(theme::tab_drop_border());
    match ix.cmp(&dragged.index) {
        Ordering::Less => style.border_l(theme::TAB_DROP_EDGE),
        Ordering::Greater => style.border_r(theme::TAB_DROP_EDGE),
        Ordering::Equal => style,
    }
})
.on_drop(cx.listener(move |shell, dragged: &DraggedTab, _, cx| shell.move_tab(dragged.id, ix, cx)))
```

`SharedString` so the drag value and the child share it without a second

## Deliberately not done

- No auto-scroll while a drag nears the bar's edge; a tab moves only onto a
  visible tab (Deferred row).
- No drop after the last tab, no drop between tabs by pointer position: the
  target is a whole tab, as in Zed.
- No drag out of the bar: dropping a tab on the sidebar, the editor or
  another window does nothing (R7). No splits (spec, Deferred).
- No `⌘⇧←`/`⌘⇧→` move by keyboard: decision 6 scoped reorder to drag. The
  palette cannot run a drag either.
- `Escape` does not cancel a drag: gpui has no such path in `div.rs`;
  releasing outside a tab does.
- Closed-stack indices are not rewritten on a move; a reopen clamps (S5).

## Risks

- **The indicator shifts layout.** A border takes layout space, so the
  target and the tabs right of it move 2 px while hovered. Zed accepts the
  same (`P:2963-2976`). If the shot shows a jitter worth fixing, a
  transparent 2 px border on every tab removes it, at the cost of the `tabs`
  shot changing.
- **A drop scrolls back to the active tab** when the user had scrolled it
  out of the bar, as every other tab operation does (Decision 5).
- **The drag preview must stay hitbox-free.** An `id` or a listener on it
  would put its hitbox over the target at mouse-up, and the drop would never
  fire. `dragging_a_tab_onto_a_later_one_puts_it_after` catches it.
- **The drag begins on the ×.** The × has only `on_click`; the press still
  reaches its tab's pending mouse-down, so a drag from the × moves the tab.
  Released back over the same ×, both the drop (a no-op onto itself) and
  the ×'s click may run, closing the tab. Rare; noted, not handled.
- **`index` in the drag value can go stale** if the bar changes during a
  drag (a load lands, `⌘W`). Only the indicator's side reads it; the drop
  reads `id`, and R3 covers a closed one.
