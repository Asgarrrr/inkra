# Decoration layer: how a feature colours the text

Status: **proposed** 2026-11-13, from a brainstorm with the owner. Fills the
"decoration layer" row of the feature registry spec's D12
(`2026-11-12-feature-registry-design.md`), and takes over the keystroke budget
that its D11 hands to "the decorations spec". Read D1, D2 and D5 first.

## Why

The registry lets a feature add commands, panes and header buttons. It cannot
yet change how the editor draws text. Code highlighting is the first feature
that needs this (`2026-11-11-code-highlighting-design.md`), and external
features will need it later.

Today highlighting is designed as a one-off: a `Highlights` global that
`line_runs` reads directly (highlighting spec, D2 and D4). This spec turns that
seam into a contract that any feature uses. Highlighting then becomes the first
client, not a special case.

This spec designs the contract and builds it with a test feature. Highlighting
moves onto it later, through a revision of its own spec.

## Terms

- **layer**: one set of decorations from one feature. A feature declares its
  layers in its `Manifest`.
- **mark**: a decoration on a byte range that restyles the text and keeps it in
  place. It is the only kind this spec builds.
- **chunk**: a part of a note's text that a feature publishes as one unit, for
  example one code block. A layer holds disjoint chunks.
- **publish**: a feature hands the core the marks of one chunk.
- **splice**: one entry of the buffer's edit log (highlighting spec, D5).
- **edit mark**: the log's monotonic counter. It is not a `Version`.

## Scope

In scope:

- the splice log in `inkra-text`, as the highlighting spec's D5 defines it;
- a layer's storage and its shift through edits, in `inkra-editor`;
- the feature contract: layers in the `Manifest`, an edit listener, publish;
- per-buffer storage in `app`, and the draw that paints layer colours;
- an open-time function, so a note lands with its colours;
- a test feature, the second implementer of the contract.

Out of scope:

- highlighting itself (its spec revision does this);
- the kinds line, replace and block (D1 names them; Deferred lists triggers);
- any mark field other than colour;
- reacting to a click or a hover on a range, and writing through a layer;
- external features and their preemption.

## Design

### D1. Four kinds are named; only mark is built

The contract names the four kinds of CodeMirror 6, which Obsidian uses:

| Kind | Effect | Example | Here |
|---|---|---|---|
| mark | restyles a range in place | a keyword in colour | built |
| line | styles a whole line | a highlighted line | deferred |
| replace | hides a range or puts a widget in its place | a formula | deferred |
| block | a widget between lines | a diagram | deferred |

Only mark is built. The layer type and the publish call carry the kind, so the
other three plug in without rewriting the first. Line, replace and block change
the layout, and D12 of the registry spec ties them to a layout slot.

### D2. A mark carries a colour only

A mark's style is `MarkStyle { color: Option<ColorToken> }`. `ColorToken` names
a field of `ThemeColors` and is generated by the `tokens!` macro
(`app/src/theme/colors.rs:4`), so a feature never holds a literal colour. A
theme switch recolours every mark with no publish.

More fields come later as more `Option`s, as in Zed's `HighlightStyle`
(`gpui/src/style.rs:580`): weight, italic, background, underline. A publish
already reshapes the affected lines (D9), so a field that changes the width
needs no new path. Repainting without a reshape, for paint-only fields, is a
later optimisation, built only after a measurement asks for it.

### D3. The core shifts the marks; the feature does nothing

After an edit, the core moves every layer's marks through the new splices. A
feature never maps positions itself.

A splice changes a mark by one rule: a mark never covers text it did not cover
before. So a colour never slides onto other letters.

- A splice before the mark shifts it by `inserted_len - removed_len`.
- A splice after the mark leaves it as is.
- A splice at the mark's start inserts before it: the new text is not marked.
- A splice inside the mark removes the removed bytes from it and splits it
  around the inserted bytes. The inserted bytes are not marked.
- A splice that covers the whole mark removes it.

So text typed inside or over a mark shows the base style until the next
publish. A feature that colours on each keystroke publishes within the same
frame, and the gap does not show.

The rule keeps three properties: marks stay sorted, disjoint, and on char
boundaries. A splice is always on char boundaries, so no rule can break one.
Chunk ranges follow the same rule as marks.

### D4. Push: the core tells the feature, the feature publishes

The core calls the feature's edit listener after each change to a note that has
the feature's layers. The listener computes on the main thread, or starts a
background task. Either way it ends with a publish. The core keeps the last
published marks, and the draw reads only the visible lines from them. The draw
never waits on a feature and never calls one.

The listener receives a `TextChange`:

- `Opened { fresh }`: the note landed. `fresh` is true when the layer's open
  function's landing succeeded (D8), even with no chunk, no lost layer cleared
  it since, and the text is still at that edit mark.
- `Edited(splices)`: the splices since the last call.
- `Lost`: the core dropped the layer's marks for this note and needs a full
  recompute. This follows a log overflow (D6) or a switch on (D10).

The listener runs once per change, after the buffer's lease drops, so it may
read the buffer. It runs for every source of change: typing, undo, paste,
reload, `apply_diff`.

A feature with no layer hears nothing. Registry D11's gate "a feature adds no
work to the keystroke path" becomes: a feature without layers adds none, and
a layer's listener is timed (D11 below).

### D5. A publish replaces one chunk

A publish names a layer, a buffer, a chunk range, the marks inside it, and the
edit mark it was computed at:

```rust
cx.publish(layer, &buffer, chunk, marks, at);
```

The core first removes the old marks inside `chunk` from the layer, trimming a
chunk that overlaps it. It then maps the new chunk forward through the splices
since `at` (D6), and inserts it. Marks outside `chunk` stay as they are.

A chunk stores its start at the layer's edit mark, and its marks relative to
that start. A splice outside a chunk moves only the start. A splice inside it
changes only that chunk's marks. One pass merges the splices against the
chunks, both sorted by offset; the highlighting spec measured this at 83 ns for
51 blocks (its D4, "Recognising an unchanged block").

A publish of the whole note is one chunk that covers the note. A feature with
no natural parts does that.

### D6. A late publish lands mapped; an overflow asks for a recompute

The core maps a publish through `edits_since(at)`, by D3's rule. Text typed
while a background task ran is therefore not coloured, and the colours around
it land in the right place.

`edits_since(at)` returns `None` once the ring dropped splices past `at`. The
core then drops the publish, clears the layer for that note, and sends `Lost`.
The same happens when a layer's own edit mark falls out of the ring, for
example after a reload that rewrites much of the note.

A layer catches up with the log at the start of every read and every publish,
so a missed listener call cannot leave a mark out of date.

### D7. Markdown stays the base; layers paint over it

Markdown is not a layer. `line_runs` builds the base runs from the markdown
spans as today. It then applies each layer's colour over them. Two things win
over every layer:

- `MARKER`: revealed syntax stays dimmed, as the highlighting spec's D2 wants
  for a revealed fence;
- the IME's marked text.

Making markdown a layer is reconsidered when line or replace marks arrive:
markdown's concealment is a replace decoration in all but name.

### D8. A note lands with its colours

A layer may declare an open function:

```rust
fn(text: &str, deadline: Instant) -> Vec<Chunk>
```

Each chunk holds its range, its tag and its marks. The function is pure,
`Send` and gpui-free.

`NoteStore::open_note` (`app/src/vault/store.rs:174`) runs the open functions
in its background task (`:192`), after the file read and before the buffer is
built. They run in catalog order and share one deadline: 8 ms after the text is
ready, the highlighting spec's landing budget (its D8). Each function stops
when the deadline passes and returns what it did.

When the note lands, the core stores the marks at edit mark 0 and records that
edit mark (`HeardLayer::land`). It calls the listener with
`Opened { fresh: true }` if the text is still there and the layer was not lost
since. The feature reads the landed chunks back and publishes the rest
later, in its own background task. The first frame with the text has the
colours the functions finished.

A function cannot be preempted. One that ignores its deadline delays the
landing; D11 logs it. The external tier needs real preemption (registry D13),
and its WASM epoch gives it.

A feature with layers activates after the first frame
(`Manifest::after_first_frame`). A note that lands before the feature activates
keeps its edit mark until the activation delivers `Opened { fresh }`.

### D9. Storage belongs to the note, not the view

The layers of a buffer live in a per-buffer global, `Decorations`, beside
`Parses` (`app/src/editor/parses.rs`). Every view of the note reads the same
marks: the editor today, a canvas card later. An entry drops when its buffer
is released, as `parsed` drops released parses.

The data and the shift are plain and gpui-free:

- `inkra-text` holds the splice log;
- `inkra-editor` holds `Layer<S>`: chunks, marks and the shift of D3. It is
  generic over the style `S` and knows no colour or theme;
- `inkra-editor` also holds `HeardLayer<S>`: a `Layer<S>` and how far its
  listener has heard the buffer. It decides the `TextChange` of D4, so the
  rules of D6, D8 and D10 live beside the data they read;
- `app` instantiates `S = MarkStyle` and converts marks into gpui `TextRun`s in
  `line_runs` (`app/src/editor/layout/runs.rs:53`). This is the only place
  that touches gpui.

A gpui fork or a second view kind therefore changes only the conversion.

`Decorations` keeps one revision counter per buffer, bumped by each publish and
each removal. `DocumentLayout::is_shaped_from` (`layout/mod.rs:128`) joins it,
so a publish reshapes the frame's lines, and a keystroke still shapes once.

### D10. Catalog order decides between layers

When two layers mark the same byte, the later one in `BUILTIN` wins the colour.
Within a feature, the later layer in the manifest wins. External features come
after built-ins, in load order. The order is stable across switches, and no
manifest field is added.

Switching a feature off removes its layers from every note; the next frame has
no colour from it. Switching it on sends `Lost` for each open note, and the
colours appear as the feature publishes.

### D11. The budget

The keystroke budget is shared and measured, not enforced, as registry D11
does for activations. Each listener call and each open function is timed. One
over 2 ms logs a line with the feature id and the layer.

The gates are count tests and one measurement:

- a keystroke shapes once, with and without a layer (`editor/tests/shapes.rs`);
- a feature without layers hears no edit;
- the keystroke cost in a code-heavy note, with the test layer on and off,
  goes in the build's PR, before/after;
- a bench of the shift for the 51-block note, to confirm it stays negligible.

### D12. The feature contract

The `Manifest` gains one field, which names something the user sees, the
colours:

```rust
pub(crate) layers: &'static [LayerDecl],
```

`LayerDecl` holds the layer's id, its kind (mark only) and its open function,
if any.

`Activation` gains one method, which adds to the handle:

```rust
on_text_change(layer, impl Fn(&Entity<Buffer>, &TextChange, &mut FeatureCx))
```

`FeatureCx` gains `publish` (D5) and `edit_mark(&buffer)`. Publishing to a
layer the feature did not declare is a caller bug and panics, as infallible
buffer operations do.

## Data flow

A keystroke in a note with the test layer:

1. `edit_buffer` runs the transaction; `Buffer::splice` logs the splice and
   bumps the edit mark.
2. The lease drops. The core calls the layer's listener with
   `Edited(splices)`.
3. The listener computes the touched chunk and publishes it at the current
   edit mark. Or it spawns a task, which publishes later at the mark it read.
4. The frame's layout sees a new decorations revision and reshapes. For each
   visible line, `line_runs` reads the marks in the line, catches the layer up
   with the log first, and paints them over the markdown runs.

A note open:

1. The background task reads the file, runs the open functions within 8 ms,
   and returns the text and the marks.
2. The buffer is built; `Decorations` stores the marks at mark 0.
3. The listener gets `Opened { fresh: true }` and publishes any chunk the open
   did not finish.

## Tests

`inkra-text`, `#[test]` plus `proptest`:

- replaying `edits_since(mark)` on the old text gives the new text, across
  edit, undo, redo and `apply_diff`;
- undo and redo increase the mark;
- more than 256 splices past a mark gives `None`.

`inkra-editor`, `proptest` on random edits and publishes:

- marks stay sorted, disjoint, inside their chunk, and on char boundaries;
- a mark never covers a byte it did not cover before the edits;
- a chunk untouched by the splices keeps its marks, shifted only;
- a publish at an old mark lands equal to a publish at the current mark,
  except on bytes inserted since.

`app`, headless `#[gpui::test]` against `MemFs`, with the test feature:

- a publish colours the runs of its range;
- a keystroke shifts the colours after it, and the typed text is not coloured;
- a late publish lands mapped;
- an overflow sends `Lost`, and a full publish restores the colours;
- switch off removes the colours on the next frame; switch on restores them;
- a note opens coloured from its open function;
- an open function past the deadline returns early, and the rest publishes
  after the landing;
- catalog order decides between two layers on the same bytes;
- a revealed marker and marked IME text win over a layer;
- two views of one buffer read the same marks.

The test feature lives under `app`'s test tree, behind `#[cfg(test)]`. It
colours a fixed word, for example every `TODO`, and can publish from a task
with a delay. It is the second implementer the contract needs (CLAUDE.md,
"Abstract only at a real seam").

After the build, render a scene with the test layer and look at it.

## Slices

Each slice ends green on `./scripts/check.sh`.

1. **The splice log.** `Splice`, the ring, `edit_mark`, `edits_since` in
   `inkra-text`, with its proptests. No caller yet.
2. **A layer and its shift.** `Layer<S>` in `inkra-editor`: chunks, publish,
   the shift of D3, catch-up, overflow. Proptests only.
3. **Publish and draw.** `Decorations`, `MarkStyle`, `ColorToken`, the
   `line_runs` merge, `is_shaped_from`. The test feature publishes once on
   `Opened` and on `Lost`. Tests: colours, shift, marker wins, two views,
   shape count. Render the scene.
4. **Edits and late publishes.** `on_text_change`, `TextChange::Edited`,
   publish at an old mark, `Lost` on overflow, the switch off and on, catalog
   order. The 2 ms log.
5. **Open with colours.** `LayerDecl::open`, the open task's step, the shared
   deadline, the seed handover, the activation that comes after a landing.
   The keystroke measurement and the shift bench.

## Deviations from Zed and CodeMirror 6

- **Colour only in v1.** Zed's `HighlightStyle` has seven fields; CM6 marks
  take any CSS class. One client needs colour. More fields are additive (D2).
- **Markdown is not a layer.** In CM6, Obsidian's markdown styling is a
  decoration like any other. Here markdown concealment changes the layout, and
  the layout has no decoration slot yet (D7).
- **Catalog order, not a declared priority.** CM6 orders by extension
  precedence; Zed by highlight key. With built-ins only, the catalog is the
  one order the user can predict (D10).
- **An open-time pure function.** Zed parses after a buffer opens, and shows
  plain text first. Inkra's open already waits for the file in a background
  task, so one more step there lands the note coloured (D8).
- **Chunked per-buffer storage.** Zed stores text highlights per display map,
  per view (`display_map.rs:232`, `highlight_text` at `:1140`), with anchors.
  Here marks belong to the buffer, so a canvas view reads them, and chunks
  keep a keystroke from touching untouched blocks (D5, D9).
- **Typed text is never coloured by a shift.** CM6 can extend a mark over text
  inserted at its edge (`inclusive`). Here the feature's next publish colours
  it (D3).

## Deviations from this spec

The build differs from the design above in these points. Code cites them by
number.

1. **The listener takes `&mut App`.** It is
   `Fn(&Entity<Buffer>, TextChange, &mut App)` (`decorations/listen.rs`). It
   takes the change by value, because `Edited` moves its splices out (D4, D12).
2. **`publish` and `drawn` are free functions** in `crate::decorations`, not
   `FeatureCx` methods. A listener reads the edit mark from the buffer, so
   `FeatureCx::edit_mark` is not built. `publish` takes a `WeakEntity`, so a
   background task does not keep a closed note alive (D12, O3).
3. **The listener hooks in `EditorView::refresh`.** `decorations::sync` runs
   first there, and the listeners run after the global is released. `refresh`
   runs for every change a view draws, reloads included, outside any lease. A
   buffer that no view shows hears its changes when a view binds it (O2).
4. **`LayerDecl` has no kind field.** It is `{ id, open }`. Mark is the one
   kind; the field arrives with a second kind (D1, D12).
5. **A chunk grows over a splice strictly inside it.** D3's rule would cut the
   chunk at a text insertion inside it. Instead, the chunk covers the inserted
   text, and its marks still follow D3. A splice at a chunk's edge or across
   it follows D3 (`map_chunk`). The feature's next publish of that chunk thus
   covers the typed text too (D3, D5).
6. **"Undeclared" means not in the catalog.** A publish to a layer that no
   feature declares panics (`rank`). A publish carries no feature, so a
   publish to another feature's layer does not panic. `on_text_change` checks
   in debug builds that its layer belongs to its feature (D12).
7. **A note launched alone gets no colours.** A note opened from the command
   line (`bootstrap.rs`, `Launch::Note`) has no vault, and with no vault no
   feature activates (`vault_features`). No layer is on, so no open function
   runs and no listener hears the note. D8 holds for every note of a vault.
8. **`ColorToken` comes from `tokens!`** (`theme/colors.rs`). The macro now
   takes `name => Variant` pairs and emits the enum and its lookup (O1).
9. **`Decorations` lives in `app/src/decorations/`**, not beside `Parses` in
   `editor/`. It follows `parses.rs`: a global keyed by the buffer's
   `EntityId`. A view other than the editor reads it too (D9).
10. **An entry drops at its buffer's release.** An entry holds no handle on
    its buffer, only a release subscription that removes it (D9). `Parses`
    drops a parse the same way, so neither an entry nor a parse waits for the
    next note.
11. **An open is fresh only at its edit mark.** The core records the edit mark
    an open landed its chunks at. If the buffer changed before the listener
    arrived, the listener hears `Opened { fresh: false }`, a full recompute
    (D8). `HeardLayer` keeps that edit mark inside its unheard state, so a
    switch or a lost layer drops it by construction.
12. **Every layer starts off.** `decorations::enable` turns a feature's layers
    on and off. A layer that is off takes no publish, hears nothing, runs no
    open function and lands nothing. Turning it off clears its marks; turning
    it on sends `Lost` (D10).
13. **`sync` bumps the revision too.** A non-empty layer behind the edit mark
    draws something else once it catches up, so the revision moves. An undo
    can otherwise bring back a version the layout shaped with older marks (D9).
14. **A late publish is bounds-checked after the mapping.** A reversed chunk
    and unsorted, overlapping or outside marks panic at once. The end of the
    text and the char boundaries are checked on the mapped chunk, against the
    current text: the text the publish was computed on is gone (D5, D6).
15. **A late publish fills around newer chunks.** Each chunk keeps the edit
    mark it was computed at. A publish leaves every chunk computed after it in
    place and lands only around them, so a byte shows the newest result that
    covers it. A whole-note recompute that finishes after the edit of one block
    therefore colours the rest of the note (D5, D6).
16. **Splices are mapped one at a time.** `catch_up` walks the chunks once per
    splice, not once for all of them. A keystroke is one splice, so it costs one
    walk; a transaction of many splices, such as `apply_diff`, costs one walk
    per splice (D5).
17. **A mark's bounds are `u32`.** A chunk stores each mark as two `u32`
    offsets from its start and the style, in a boxed slice with no spare
    capacity: 12 bytes a mark for a one-byte style. A load is capped at
    `MAX_TEXT_BYTES`, but a paste grows a buffer with no cap. So when one
    bound lies more than `u32::MAX` bytes past the chunk's start, the chunk
    holds no mark and no tag (`Chunk::new`, D5). Its feature sees an untagged
    chunk and republishes it. From S2a the syntax layer never loops on it: a
    block over `BLOCK_LIMIT` gets an empty chunk, which keeps its tag (code
    highlighting spec, deviation 11).

## Deferred

| Item | Trigger |
|---|---|
| line marks | a feature that styles whole lines (a highlighted search hit line) |
| replace and block kinds | the floor-2 inline element of registry D12 and its layout slot |
| weight, italic, background, underline | a feature that needs one; background also needs rectangles behind runs |
| repaint without reshape | a measurement showing a publish's reshape costs a frame |
| markdown as a layer | line or replace marks exist |
| click and hover on a range | a feature that reacts to its marks (a link preview) |
| writing through a layer | a feature that edits text it decorates; it goes through `transact_at` |
| auto-disable after overruns, preemption | the external tier |
| highlighting on this contract | its spec revision; blocked on the `streaming-iterator` waiver and, for its S3, the six stale grammars |

## Open questions

- **O1. `ColorToken` from `tokens!`.** The macro lists every `ThemeColors`
  field, so it can emit the enum and its lookup. Slice 3 confirms this, or
  falls back to a hand-written enum of the tokens a layer may use. Resolved:
  deviation 8.
- **O2. Where the listener hooks.** The listener must run once per change and
  after the lease drops. An observer of each live buffer in `NoteStore` fits;
  an `edit_buffer` hook misses reloads. The plan picks one and states why.
  Resolved: deviation 3.
- **O3. A publish for a released buffer.** A background task can finish after
  its note closed. The publish should be a no-op, not a panic. The plan checks
  that `Decorations` can tell. Resolved: deviations 2 and 10.
